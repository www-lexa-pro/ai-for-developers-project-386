# Реализация спецификации #5

## Каталог и прямые ссылки — #6

16 ноября 2026 года реализован каталог из API и страница выбранного типа.
Типы хранятся в памяти экземпляра сервера; новый экземпляр создаёт три начальных
типа с новыми случайными идентификаторами. Список сохраняет порядок создания.
Старый или неизвестный идентификатор возвращает 404 с постоянным кодом
`meeting_type_not_found` и сообщением «Этот тип встречи больше недоступен».

Контрактная цепочка:

1. `api/main.tsp`: `MeetingType`, `listMeetingTypes`, `getMeetingType`.
2. `mise run generate` создаёт `api/generated/openapi.yaml`,
   `frontend/src/api/` и `backend/internal/api/generated.go`.
3. `backend/main.go`: HTTP-обработчики сгенерированного интерфейса,
   начальные типы и сохранённый health.
4. `frontend/src/App.tsx`: вызовы сгенерированного SDK; каталог и прямой адрес
   `/meeting-types/{id}`; ожидание, ошибка с ручным повтором, пустой список,
   недоступный тип и возврат. Запоздавшее чтение не подменяет актуальный экран.

Проверки включены в `mise run check`:

- `backend/catalog_test.go`: HTTP-каталог, порядок и данные, чтение,
  новые идентификаторы у нового экземпляра и недействительность старых ссылок.
- `backend/main_test.go`: сохранённый дымовой тест сборки и запуска отдельного
  процесса с чтением health.
- `frontend/tests/catalog.test.tsx`: действия пользователя и видимые состояния;
  управляемые ответы только на сетевой границе, SDK остаётся настоящим.

Наблюдавшиеся red → green:

- Каталог: HTTP 200 с пустым списком вместо трёх типов → начальные типы из памяти.
- Чтение: HTTP 404 для существующего идентификатора вместо 200 → операция
  TypeSpec, генерация и обработчик чтения.
- Интерфейс: отсутствует описание из API → загрузка через SDK и выбор типа.
- Повторный переход на главную: каталог исчезает и остаётся ожидание → переход
  к уже открытому адресу сохраняет экран.

Проверка сброса идентификаторов использует два независимых экземпляра
HTTP-приложения в одном тестовом процессе; запуск отдельного процесса покрыт
существующим дымовым тестом health. Бронирования, создание дополнительных типов,
календарь и страница владельца относятся к следующим дочерним задачам.

Итог локальной проверки 16 ноября 2026 года: `mise run check` прошёл полностью:
линтеры без замечаний, TypeScript, 3 Go-теста, 8 пользовательских тестов,
сборки Go/Vite и проверка актуальности генерации. Работающая система и remote
не изменялись; успешный локальный check не подтверждает GitHub Actions.

## Доступность и выбор времени — #8

16 ноября 2026 года добавлена операция `GET /api/meeting-types/{id}/availability`.
Ответ включает московский часовой пояс, первую и последнюю даты окна и все
14 дат единого снимка. Сервер сообщает причины недоступности `weekend` и
`fully_booked`; слоты содержат точное начало и окончание с часовым смещением.

`backend/schedule.go` получает текущее время, длительность и занятые интервалы
явно. В нём нет собственного чтения часов или хранилища. HTTP-обработчик получает
время и рассчитывает весь снимок под общей блокировкой календаря. Эта же
блокировка защищает чтение типов и предназначена для записи в следующей #9.
Начала идут каждые 30 минут; пересечения учитывают все занятые интервалы,
касание границ разрешено. Неизвестный тип возвращает прежний код 404.

`AvailabilityPicker` использует сгенерированный SDK и отдаёт выбранный слот
родителю через `onSelectionChange`. Дата и время выбираются вручную. Даты без
слотов заблокированы; смена даты использует загруженный снимок. Смена типа
немедленно скрывает прежние слоты и игнорирует запоздалые ответы. Обновление
сбрасывает время и сохраняет только всё ещё доступную дату. Есть загрузка,
ошибка с ручным повтором и пустое окно; отправка бронирования относится к #9.
`BookingPage` подключён к прямой странице выбранного типа.

### Проверки и наблюдённый TDD — #8

Согласованные границы: HTTP API с управляемыми часами; действия пользователя
с настоящим SDK и управляемым сетевым ответом. До появления POST /bookings
занятые интервалы и дополнительные длительности задаются внутренними fixtures.

- Первый RED: отсутствует зависимость `server.now` (ошибка компиляции).
- Следующий RED: HTTP 404 на запрос доступности вместо 200.
- GREEN: контракт TypeSpec, генерация, чистые правила и HTTP-обработчик.
- UI RED: отсутствует видимое ожидание загрузки; GREEN: загрузка через SDK,
  ручной выбор даты и времени, московское отображение и причины недоступности.
- HTTP-проверки покрывают московскую полночь, точные границы 14 дат,
  выходные, длительности 1/15/30/45/540, рабочие часы, частичные пересечения
  и допустимое касание границ, причины недоступности и неизвестный тип.
- UI-проверки покрывают отсутствие автоматического выбора, смену даты без
  запроса, обновление с сохранением/сбросом даты, сброс времени, ошибку/повтор,
  пустое окно, исчезнувший тип и запоздавший ответ при смене типа.

До интеграции `mise run check` прошёл полностью: линтеры без замечаний, Go HTTP
и дымовые тесты, 14 UI-тестов (включая каталог #6), TypeScript, сборки Go/Vite
и проверка актуальности генерации. Часовая база встроена через `time/tzdata`,
поэтому Europe/Moscow не зависит от настройки операционной системы.
Remote и работающая система не изменялись.
