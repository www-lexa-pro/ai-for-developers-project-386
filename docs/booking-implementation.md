# Реализация спецификации #5

## Каталог и прямые ссылки — #6

16 ноября 2026 года реализован каталог из API и страница выбранного типа.
Типы хранятся в памяти экземпляра сервера; новый экземпляр создаёт три начальных
типа с новыми случайными идентификаторами. Список сохраняет порядок создания.
Старый или неизвестный идентификатор возвращает 404 с постоянным кодом
`meeting_type_not_found` и сообщением «Этот тип встречи больше недоступен».

Контрактная цепочка:

1. `api/main.tsp`: `MeetingType`, `listMeetingTypes`, `getMeetingType`.
2. `mise run generate` создаёт `api/generated/openapi.yaml`,
   `frontend/src/api/` и `backend/internal/api/generated.go`.
3. `backend/main.go`: HTTP-обработчики сгенерированного интерфейса,
   начальные типы и сохранённый health.
4. `frontend/src/App.tsx`: вызовы сгенерированного SDK; каталог и прямой адрес
   `/meeting-types/{id}`; ожидание, ошибка с ручным повтором, пустой список,
   недоступный тип и возврат. Запоздавшее чтение не подменяет актуальный экран.

Проверки включены в `mise run check`:

- `backend/catalog_test.go`: HTTP-каталог, порядок и данные, чтение,
  новые идентификаторы у нового экземпляра и недействительность старых ссылок.
- `backend/main_test.go`: сохранённый дымовой тест сборки и запуска отдельного
  процесса с чтением health.
- `frontend/tests/catalog.test.tsx`: действия пользователя и видимые состояния;
  управляемые ответы только на сетевой границе, SDK остаётся настоящим.

Наблюдавшиеся red → green:

- Каталог: HTTP 200 с пустым списком вместо трёх типов → начальные типы из памяти.
- Чтение: HTTP 404 для существующего идентификатора вместо 200 → операция
  TypeSpec, генерация и обработчик чтения.
- Интерфейс: отсутствует описание из API → загрузка через SDK и выбор типа.
- Повторный переход на главную: каталог исчезает и остаётся ожидание → переход
  к уже открытому адресу сохраняет экран.

Проверка сброса идентификаторов использует два независимых экземпляра
HTTP-приложения в одном тестовом процессе; запуск отдельного процесса покрыт
существующим дымовым тестом health. Бронирования, создание дополнительных типов,
календарь и страница владельца относятся к следующим дочерним задачам.

Итог локальной проверки 16 ноября 2026 года: `mise run check` прошёл полностью:
линтеры без замечаний, TypeScript, 3 Go-теста, 8 пользовательских тестов,
сборки Go/Vite и проверка актуальности генерации. Работающая система и remote
не изменялись; успешный локальный check не подтверждает GitHub Actions.
